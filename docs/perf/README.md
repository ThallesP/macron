# What would make games faster on a real Apple-silicon Mac

## Thalles: the two-minute version (night of 2026-11-15 to 16, measured on your M3)

**What was established**

- In the practice range Overwatch waits on the GPU (15.7 ms of GPU work a frame). DXMT is not wasting it: on the same work it costs 3 to 5% more GPU time than native Metal. The time goes into pixels, so rendering fewer of them is the lever.
- DLSS can run on your Mac: with a switch, DXMT turns a game's DLSS into Apple's MetalFX upscaler, and on your M3 the upscaler is created. Not tried in Overwatch yet (that needs you).
- Overwatch's menu waits on the CPU, not the GPU (GPU busy 40%, 54 fps). One of the game's threads checks the same eight Windows events about 43,000 times a second, and each check is a trip to Wine's server (8 µs on your Mac). A Wine fix that answers those checks inside the game is designed, not built.
- Memory (the memory thread's work): with its DXMT fix, Overwatch on that screen takes 3.4 GB instead of 14.25 GB, and the swapping that came with it goes.
- Your MacBook Air throttles within about a minute of a full game; a GPU-only load at 60 fps did not throttle in five minutes.
- Closed: advertising AVX to games (slower under Rosetta); Apple's D3DMetal (would need a second Wine).

## What batch 1 showed that changes how to read every number

- **The fanless MacBook Air throttles inside every benchmark run.** Each Superposition run starts at thermal pressure level 0 (the script waits for it) and reaches level 2 within about a minute in nearly every 200 s run (`thermal.txt` per second). Two identical 1600x900 runs differed by 4% in the benchmark's FPS (50.9 and 48.7); runs at other settings had different thermal histories, so differences between settings smaller than the thermal effect are not established by these runs. Batch 2's request 12 measured the thermal effect itself with a fixed load: see "Heat".
- **The Metal HUD's GPU time is a span, not busy time.** At 1600x900 its median GPU time a frame (21 to 24 ms) is longer than the frame interval (GPU busy 116 to 118%), and native Metal at 137 frames a second shows 12.9 ms a frame, in both the HUD and Metal's own `GPUEndTime - GPUStartTime`: with several frames in flight, a command buffer's start-to-end time includes time it waits behind others. So HUD GPU times compare only between runs with the same pacing, and none of them is a frame's GPU cost. Request 11's Metal System Traces give the GPU's own pass times.
- **The HUD writes each frame's record twice.** Request 13's raw lines (`metal-HUD: 69,52.31,208.43,16.67,11.43,16.67,11.78,16.67,11.78,16.67,11.93,16.67,11.93,…`) carry each interval and GPU time pair twice in a row, in the HUD's own line; so the doubled rows are the HUD's, not the parser's. Counts of HUD frames are twice the frames; rates, medians and percentiles are unaffected.
- **The HUD's frames are not the game's frames.** Superposition counted 49 to 104 FPS where the HUD counted 46 to 60; `gpuload.exe` through DXMT returned from `Present` 120.0 times a second (its own clock, all three loads) while the HUD counted 60.0; native `gpuload` counted the same in both (134 to 248). Every HUD frame record also appears twice in a row (50 to 56% of rows, every run, native too; the HUD's own doing, above).

### 1. DLSS through MetalFX: DXMT's NVIDIA extension (`DXMT_ENABLE_NVEXT=1`)

DXMT answers a game's DLSS calls with Apple's MetalFX temporal upscaler, so a game that offers DLSS renders at a lower resolution and MetalFX rebuilds the full-size picture.

- **source:** DXMT 0.80 ships `nvapi64.dll` and `nvngx.dll`; with `DXMT_ENABLE_NVEXT=1` the adapter reports NVIDIA's vendor id (0x10de, `dxgi_adapter.cpp`), NVAPI reports an RTX 4090 (`nvapi.cpp`, `NvAPI_GPU_GetArchInfo`), NGX reports super resolution available unconditionally, and `NVSDK_NGX_D3D11_CreateFeature` creates a MetalFX temporal scaler (`nvngx.cpp`). Without the variable nothing changes. DXMT's wiki says not to turn it on for every game, because a game that believes it is on NVIDIA may take paths that are only fast there.
- **source:** Macron already installs both DLLs: a DXMT prefix made by Macron has `nvngx.dll` and `nvapi64.dll` in `system32` (checked on the sandbox). Macron never sets the variable.
- **sandbox** (`tools/perf/nvprobe.cpp`, through `macron waitforexitandrun` and the Steam bridge's `steam.exe`, so the way Steam starts a game): without the variable the adapter is `0x106b` and `nvngx.dll` does not load; with `DXMT_ENABLE_NVEXT=1` the adapter is `0x10de`, `NvAPI_Initialize` succeeds, NGX init succeeds and reports `SuperSampling.Available=1`, and creating the DLSS feature fails with `0xbad0001` (feature not supported): the virtual GPU has no MetalFX temporal scaler.
- **Overwatch:** offers DLSS, FSR 2.2 and FSR 1 ("High-Quality Upsampling"); DLSS or FSR 2.2 cap the render scale at 67% ([PCGamingWiki](https://www.pcgamingwiki.com/wiki/Overwatch_2), [Blizzard forum](https://us.forums.blizzard.com/en/overwatch/t/custom-render-scale-option-maxes-at-67/874131)). At 67% the game shades 45% of the pixels.
- **M3** (request 1, `nvprobe` through `macron waitforexitandrun`): with `DXMT_ENABLE_NVEXT=1` the adapter is `0x10de`, `NvAPI_Initialize: OK`, `NGX init: OK`, and `DLSS feature 1280x720->1920x1080: created (MetalFX temporal scaler)`; without it the adapter is `0x106b` and `nvngx.dll` does not load (error 1114). So on the M3 a game's DLSS calls do reach a working MetalFX temporal scaler through Macron as installed.
- **not run, Thalles's to decide:** starting Overwatch on his own account with the game told the GPU is NVIDIA's (request 6, start 2); it has anti-cheat.
- **Ready for the pre-release, off by default:** a `dlss` switch file (`~/Library/Application Support/Macron/dlss`): while it exists, macron starts DXMT games with `DXMT_ENABLE_NVEXT=1`. Not a profile that turns it on for Overwatch by itself: whether Overwatch on his account should see an NVIDIA GPU is his decision. To try: `touch` the file, start Overwatch, choose DLSS in its video settings; the Metal HUD then shows "MetalFX: Temporal" and the scale.
- **pending:** whether Overwatch loads `nvngx.dll` and offers DLSS under DXMT; what share of Overwatch's GPU time scales with pixels (request 3's sweep is the stand-in); how MetalFX temporal looks and costs in the game (Thalles, by hand: it needs a settings change in his account).
- **If it holds:** a per-game profile switch (`env` in `fixes/games/<id>.json`) for games known to work, not a default.

### 2. Rendering fewer pixels: what DXMT really renders at

DXMT renders at exactly the size the game asks for, and on a Retina Mac that size is in points, not pixels.

- **source:** Wine's Mac driver has Retina mode off unless the `RetinaMode` registry value is set (`retina_enabled = false`, `macdrv_main.c`), so Windows sees display modes in points and window layers have `contentsScale` 1.0 (`cocoa_window.m`). DXMT's back buffer is the swap chain's size and its layer's drawable is that size times the MetalFX factor, 1 without MetalFX (`d3d11_swapchain.cpp`, `ResizeBuffers` and `ApplyLayerProps`).
- So Overwatch's 1920x1243 display mode is 1920x1243 pixels (2.4 million), and macOS's compositor scales it up to the 2880x1864 panel (5.4 million). Nothing is spent rendering at Retina resolution; there is no Retina waste to remove. The lever is the other way: fewer pixels and a good upscale (candidates 1 and 4, or the game's own render scale and FSR 1).
- **M3, Superposition medium, windowed, the benchmark's own FPS** (`m3-batch1/`): 1600x900 (1.44 million pixels) 50.9 and 48.7; 1280x720 (0.92 M) 76.0; 960x540 (0.52 M) 79.4; 640x360 (0.23 M) 96.3. Going from 1.44 to 0.92 million pixels gave 52% more frames; below that, 44% and then 75% fewer pixels gave 4% and 21% more, and the HUD's GPU busy fell to 63% and 53%. So in this benchmark on the M3 the frame is pixel-bound around 1600x900 and bound by something else (the engine's CPU side under Rosetta, DXMT's encoding, or fixed GPU work) at about 10 to 13 ms below 1280x720. Thermal histories differed between these runs (above), so the exact figures are soft; the shape is not.
- For Overwatch (1920x1243, 2.39 million pixels, GPU-bound at 15.7 ms) this says rendering fewer pixels is the lever with room; it does not say how much Overwatch's own floor is. That needs Overwatch at a lower render scale, which is Thalles's to set. If it falls in proportion to pixels, upscaling pays; if a large part stays fixed, that part is per-frame work (DXMT's or the game's) and the next step is a Metal System Trace.

### 3. macOS Game Mode for Wine's processes

macOS gives Game Mode (CPU and GPU priority for the game, background work held back) only to processes whose app bundle says they are a game, and a Wine process is no app bundle.

- **sandbox:** with the stock runtime, RunningBoard sees every Wine process as `anon<wine>` and `gamepolicyd` labels none of them, focused or not. Writing `LSApplicationCategoryType = public.app-category.games` into the Info.plist embedded in Wine's loader (re-signed) changes nothing: still `anon<wine>`.
- **source:** Wine starts every Windows process, the game included, by running `lib/wine/x86_64-unix/wine` (`wineloader` in `dlls/ntdll/unix/loader.c` is the realpath of `ntdll.so`'s folder plus `wine`), and that loader opens the `ntdll.so` beside the realpath of itself (`loader/main.c`).
- **sandbox:** so `tools/perf/gamemode-bundle.sh` moves that loader into `Macron Game.app/Contents/MacOS/wine` (with `ntdll.so` linked beside it and a games-category Info.plist) and leaves a symlink at the old path. Then `gamepolicyd` logs `Found game GameProcess(Optional("wine"), pid=…, labelReason=infoPlist)` for every Wine process, the Game Mode rocket appears in the menu bar, Game Mode goes to `paused` while the focused game is windowed, and the Direct3D 11 probe draws as before. The first start of the bundle asked once "Allow "Macron Game" to find devices on local networks?" and Wine waited until it was answered.
- **pending:** whether Game Mode turns `on` for a full-screen game on the M3, and whether it changes frame times at all (request 5).
- **M3:** the Metal HUD shows a "Game Mode" line ("Off" in batch 2's windowed screenshots), so a run can show whether it was on without reading `gamepolicyd`'s log.
- **Ready for the pre-release, off by default:** `macron` has it (`internal/wineruntime/gamemode.go`): while `~/Library/Application Support/Macron/game-mode` exists, each launch puts both Wine trees' loaders into the bundle, and takes them out again when the file is gone; `macron uninstall` removes the file. It ships as a switch, off, so that Thalles can try it (`touch ~/Library/Application\ Support/Macron/game-mode`, start a game full screen, answer macOS's local-network question once); turned on by default only if frame times show it helps. Nobody has published frame times for Wine under Game Mode; the projects that do the same ([highball #338](https://github.com/gauthierpiarrette/highball/issues/338), [Yaagl #773](https://github.com/yaagl/yet-another-anime-game-launcher/issues/773)) checked only that it turns on, and Yaagl reports audio problems for some users.

### 4. MetalFX spatial upscaling in the swap chain (`DXMT_METALFX_SPATIAL_SWAPCHAIN=1`)

DXMT can upscale the game's finished frame with MetalFX before presenting it, so the picture is sharp on a Retina screen while the game renders the smaller size.

- **source:** with the variable, the swap chain keeps the game's back buffer at the size the game asked for and presents a MetalFX spatial upscale of it, `d3d11.metalSpatialUpscaleFactor` times larger (default 2, set through `DXMT_CONFIG="d3d11.metalSpatialUpscaleFactor=1.5"`).
- It adds GPU work (the upscale and a larger drawable); it only saves time together with a lower game resolution. For Overwatch, the game's own render scale with FSR 1 is the same idea, inside the game.
- **M3** (request 4, both 800x450 rendered, windowed): without MetalFX 78.7 FPS, HUD GPU time median 9.73 ms; with `DXMT_METALFX_SPATIAL_SWAPCHAIN=1` (upscaled to 1600x900) 104.0 FPS, 9.99 ms. The upscaled run spent most of its 200 s at thermal level 0 and the other mostly at level 2, so its higher FPS is the cooler Mac, not MetalFX. What holds: the 2x MetalFX spatial upscale to 1600x900 adds about 0.26 ms to the HUD's GPU time a frame, while rendering 1600x900 itself took 21 to 24 ms there. A game rendered at a quarter of the pixels and upscaled by DXMT costs a fraction of rendering them all; the picture was not looked at. - **M3, alternating order** (request 14, `m3-batch2/abba-*`, 800x450 rendered, off, on, on, off, all four mostly at thermal level 2 by the end): without MetalFX 91.1 and 84.6 FPS, HUD GPU time median 9.61 and 9.64 ms; with it 85.6 and 81.0 FPS, 10.06 and 10.31 ms. So the 2x MetalFX spatial upscale to 1600x900 costs about 0.56 ms of GPU time a frame (+5.8%) and about 5% of the benchmark's frame rate (87.9 to 83.3 on average). The HUD in the `on` screenshot reports "MetalFX Spatial, 800x450 to 1600x900" and a 1600x900 layer; the two screenshots are of different scenes, so they do not compare the picture side by side. Against rendering 1600x900 itself (50.9 and 48.7 FPS in batch 1), rendering a quarter of the pixels and upscaling ran at about 83: in this benchmark, on this Mac, roughly 1.7 times the frame rate for a full-size picture.

### 5. GPU work DXMT does that a native renderer would not

- **source:** presenting is one extra full-screen pass: DXMT draws the back buffer into the drawable with a full-screen triangle (load action DontCare, store Store; `dxmt_presenter.cpp`). At Overwatch's 2.4 million pixels that is reading and writing about 20 MB a frame. DXMT's shader compiler emits fast math unless HLSL marks an instruction `precise` (`airconv`, `UseFastMath`). It lets the GPU fall up to 3 frames behind (`max_latency_ = 3`), which is the usual depth. None of this stands out.
- **source and sandbox:** Overwatch's `CreateGeometryShaderWithStreamOutput: not supported, expect problem` is DXMT emulating stream output; Unigine Superposition hits the same line on the sandbox (`warn: Emulate stream output`).
- **pending:** the GPU busy share (GPU time over frame interval) in the benchmark (request 2) and in Overwatch's menu (request 6). A frame interval much longer than the GPU time means the GPU waits on something.
- **M3, the direct measure** (request 10, `m3-batch2/m3sync-*`, both sides presenting at the display's 60 a second, the HUD's GPU time median): full-screen passes `fill` 14.22 ms through DXMT against 14.28 (native x86_64) and 14.36 (native arm64); `mix` 14.21 against 13.57 and 13.59 (+0.64 ms, +4.7%); 4,000 draws `draws` 0.98 against 0.77 and 0.77 (+0.21 ms, about 50 ns of GPU time a draw).
- **M3, the GPU's own record** (request 11, Metal System Traces of `fill` at 60 a second, `tools/perf/gpu-intervals.py` on `trace-*-metal-gpu-intervals.xml.gz`): fragment work 831.8 ms per second of trace through DXMT against 811.1 natively (+2.6%, about 0.34 ms a frame, DXMT's extra present pass included); vertex work 37.4 against 38.0. The Superposition trace did not record (`xctrace` ran past its limit and the export said the trace was malformed).
- **Closed:** DXMT's translated shaders and its passes cost what native ones do, within 3 to 5%, on these loads. That cannot account for Overwatch's 15.7 ms. Not covered: shaders much more complex than these, and DXMT's stream-output emulation, which Overwatch uses.
- Earlier, uncapped (request 8, superseded): `tools/perf/gpuload.c` (Direct3D 11, through DXMT) and `tools/perf/gpuload.m` (the same passes, shader math, draws and per-draw constants in native Metal, its layer set up as Wine's and DXMT's are) on the same M3, for full-screen shader passes, for 4,000 small draws with per-draw constants, and for both. The GPU time a frame of the two is what DXMT adds to the same work, presenting pass included. Both run and quit by themselves on the sandbox (its numbers say nothing about speed). One difference that is not DXMT's: the Direct3D 11 program's shaders are compiled at run time by Wine's own HLSL compiler, not by Microsoft's, as a shipped game's would be.

### 6. Wine server round trips (msync, or a Mac backend for Wine's in-process sync)

A Windows wait, event, semaphore or mutex operation under this Wine is a request to the `wineserver` process and back; msync and its kind do those in the game's own process instead.

- **M3:** a wineserver round trip costs 8.1 µs and this Wine has no msync or esync (`macron diagnose`).
- **M3, Overwatch after its start, left alone 185 s** (request 6 start 1, `m3-batch1/ow-1/`): 53.5 to 54.6 frames a second, frame interval median 18.27 ms, GPU time median 7.77 ms, **GPU busy 40%**; `top` over 20 s: the game 100 to 104% of a core, **`wineserver` 51 to 55% of a core**. On that screen the GPU is not the limit and the server does half a core of work for the game. (In the practice range the GPU was the limit at 15.7 ms; these are different screens.)
- **source, Wine 11.21:** Wine now has a layer for synchronisation done in the game's process, `inproc_sync` (`dlls/ntdll/unix/sync.c`, `server/inproc_sync.c`): nine operations (semaphore release and query, event set, reset, pulse and query, mutex release and query, wait for any or all), with a handle cache in each process and the objects kept alive by the server. Its only backend is Linux's `ntsync` kernel driver: the server creates a kernel object per Windows object and hands its file descriptor to clients. Without `linux/ntsync.h` every operation returns `STATUS_NOT_IMPLEMENTED` and Wine falls back to the server. On a Mac that is always the case.
- **source, msync:** the newest patch set ([marzent/wine-msync](https://github.com/marzent/wine-msync), `msync-devel.patch`) is for Wine 9.15 (August 2024): about 3,500 added lines in about 40 files of the server and `ntdll`, every waitable server object given a shared-memory slot (the esync design), waits through Mach semaphores and the private `__ulock_wait2` and `mach_msg2_trap`. Wine's synchronisation was rebuilt around `inproc_sync` since then, so porting it to 11.21 is a reimplementation, not a rebase.
- **What porting takes (not built):** either msync carried forward onto 11.21's server code, or a Mac backend for the nine `inproc_sync` operations, where the server makes a shared-memory object instead of an `ntsync` one and clients wait on it in their own process. The hard part on either path is the same: waiting on several objects at once (wait-any and wait-all across processes, with timeouts and APCs), which `ntsync` does in the kernel and a Mac has no kernel object for.
- **M3, request 15** (`m3-batch2/ow-server/`, 5 s of the menu with Wine's server trace on; the game kept its usual frame rate): **266,302 server requests in 5 s, about 53,000 a second.** `select` (waits) 228,472 (86%), `event_op` 12,275, `close_handle` 9,759, `create_event` 8,838, `release_semaphore` 2,637; nothing else above 600. Of the waits, **212,247 had a zero timeout** (a poll: "is this signalled right now?"), 13,125 waited without a timeout and 2,227 with one. **One thread made 202,368 of the requests, all `select`**: about 40,000 polls a second. A second thread creates an event, waits on it and closes it about 1,800 times a second each.
- So the server's half core is synchronisation, and four fifths of it is one thread polling. At 8.1 µs a round trip that thread spends about 0.33 s of every second waiting for the server's answer, about 6 ms of each 18.3 ms frame (40,000 polls a second over 54 frames is 750 polls a frame); on Windows a poll that finds nothing signalled costs well under a microsecond. Whether that thread holds up the frame is not established. **M3, request 17** (`m3-batch3/ow-handles/`): the polling thread made 217,860 zero-timeout waits in 5 s (about 43,600 a second) on eight handles, each made by `create_event`: the polled objects are plain events, the simplest case for the fix below. **M3, request 16** (`m3-batch3/ow-sample.txt.gz`) was meant to show whether that thread is the one holding the frame, and cannot: under Rosetta `sample` ends almost every thread's stacks in `??? (in <unknown binary>)`, and Wine's `ntdll.so` frames are unnamed (its local functions have no symbols; `atos` resolves none of the 29 offsets), so a thread waiting on the server cannot be told from one running game code (`tools/perf/sample-threads.py`).
- **source:** the poller is not DXMT. DXMT's own CPU waits are `std::atomic` waits (`util/util_cpu_fence.hpp`), which Wine turns into `RtlWaitOnAddress`, not server requests; its only `WaitForSingleObject` waits are without a timeout (`util/thread.hpp`). The polls come from the game's code.
- **A smaller change than msync covers most of it (not built):** a poll that finds nothing signalled could be answered in the game's own process if the server published each event's, semaphore's and mutex's signalled state into shared memory, as Wine 11 already does for some window state. A zero-timeout wait would read the states of its objects there and return "timed out" without a request when none is signalled (a snapshot taken a moment earlier is as valid an answer as the server's); any other wait, and any poll that finds something signalled (which then has to be consumed atomically), goes to the server as now. That would remove about 212,000 of the 266,000 requests in request 15's five seconds, and none of the hard part of msync (waiting on several objects across processes) is needed. Mutexes need care (a mutex owned by the polling thread counts as signalled for it). It is a Wine patch in the server's event, semaphore and mutex objects, one request to find an object's slot (cached per handle, as `inproc_sync` caches), and the zero-timeout path in `ntdll`'s waits.
- **Ranked third:** it is the only measured cost on the CPU-bound screen, and it does nothing for the GPU-bound practice range.

### 7. AVX under Rosetta (`ROSETTA_ADVERTISE_AVX=1`)

Rosetta can run AVX and AVX2 code but hides them from CPUID unless the variable is set.

- **sandbox** (`tools/perf/avxprobe.c`, through `macron waitforexitandrun`): without the variable a Windows program under Macron sees no AVX, AVX2, FMA, F16C or BMI, and `IsProcessorFeaturePresent(PF_AVX_INSTRUCTIONS_AVAILABLE)` is false; with it, all of them are present, XCR0 is 0x7 and `GetEnabledXStateFeatures` is 0x7. The same float kernel (4096 floats in L1, 200,000 passes) was slower as AVX2+FMA than as SSE2 in all seven runs: 1.16, 1.17, 1.30, 1.44, 1.50, 1.56 and 1.81 times the SSE2 time (the sandbox's absolute speed varied from 8 to 21 GFLOP/s between runs, the ratio less). **AVX2 code is slower than SSE2 code under Rosetta here.**
- **M3** (request 1): with the variable, the AVX2 kernel took 1.48 times the SSE2 time in four runs out of four (19.4 against 28.8 GFLOP/s). Closed: a compatibility switch, not a speed-up. The sandbox's CPU cores are real Apple cores, and this kernel makes no system calls, so the ratio should hold on the M3 (request 1 checks).
- So it is a compatibility switch for games that refuse to start without AVX (CrossOver turns it on per game), not a speed-up; turned on for every game it can make games that pick an AVX path slower.

### 8. D3DMetal (Apple's Game Porting Toolkit) installed by the user

- Apple's licence does not let Macron ship D3DMetal. CrossOver bundles it and picks DXMT, D3DMetal or wined3d per game from its own database ([CrossOver 25](https://www.codeweavers.com/crossover/changelog)). Whisky imported a user's Game Porting Toolkit by copying the toolkit's `redist/lib/external` (`D3DMetal.framework`, `libd3dshared.dylib`) into its Wine's `lib/external` ([AppleGamingWiki](https://www.applegamingwiki.com/wiki/Game_Porting_Toolkit)).
- **sandbox:** the `ntdll.dll` of Macron's Wine 11.21 exports `__wine_unix_call_dispatcher` and not `__wine_unix_call`. Its `winemac.so` exports `macdrv_functions` (Macron's Wine patch 0001, for DXMT), which D3DMetal is also reported to read.
- **reported by others, not checked here** (no toolkit on the sandbox: Apple's download needs a developer sign-in): D3DMetal's DLLs import `ntdll.__wine_unix_call`, so they do not load on upstream Wine 10 and later; with that export restored they crash in `pthread_self`; on CrossOver-based Wine (CrossOver 24's Wine 9, Gcenx's game-porting-toolkit builds) they create Direct3D 11 and 12 devices ([codeWonderland/neutron #3](https://github.com/codeWonderland/neutron/pull/3), [Zonatto-Luiz/cellar](https://github.com/Zonatto-Luiz/cellar), [WineForge](https://github.com/Alien4042x/WineForge), which patches Wine 11 to load it).
- So what a user who installs the toolkit himself would need from Macron: a Wine tree D3DMetal runs in (CrossOver's source, as Cellar builds, or upstream Wine with the loader changes WineForge carries), the toolkit's `redist/lib/external` (`D3DMetal.framework`, `libd3dshared.dylib`) and its Windows DLLs copied from his own download into that tree, and `dxgi,d3d11,d3d12` set to native for the game. Macron would find the toolkit on his disk and never ship it. It is a second Wine runtime and a new backend; whether D3DMetal beats DXMT on Overwatch is not known, so it stays last.

## What goes into the pre-release

Only what is measured to work and cannot hurt anyone who does not turn it on:

- `~/Library/Application Support/Macron/dlss`: DLSS through MetalFX for DXMT games (candidate 1). Measured on the M3: the DLSS feature is created through MetalFX's temporal scaler. Not measured: a game's frame rate with it.
- `~/Library/Application Support/Macron/game-mode`: Wine's loader in a games-category bundle, so macOS can give Wine games Game Mode (candidate 3). Measured on a sandbox: every Wine process labelled a game, the Direct3D 11 probe drawing as before, the switch undone cleanly. Not measured: Game Mode turning on full screen on the M3, and frame times with it.

Both are in `macron`, are removed by `macron uninstall`, and are described in README.md's launcher section. **Published in [v0.5.0-rc3](https://github.com/ThallesP/macron/releases/tag/v0.5.0-rc3)**, which passed `gate3.sh`, the Steam bridge check and a check of both switches from the installed package on a fresh sandbox before publishing (sbx_vubspulo, `docs/proof/release-0.5.0-rc3/`): with `dlss` the adapter is `0x10de` and without it `0x106b`; with `game-mode` the Direct3D 11 probe presents (60 frames in 810 ms), `gamepolicyd` labels it a game, and removing the file restores Wine's loader with a valid signature and no bundle left. Everything else on the list is either closed, a setting in the game (render scale, frame limiter), or not built (an msync port).

## The benchmark

`tools/perf/bench.sh` runs a free Unigine benchmark through `macron waitforexitandrun` with the default DXMT profile, so the installed Macron 0.4.0 needs nothing new: Superposition 1.1 (64-bit, Direct3D 11, 2017) or, as a fallback, Heaven 4.0 (32-bit, 2013). Each plays its own fixed camera path in a window and quits by itself (Superposition's benchmark mode `-mode 2`, Heaven's Phoronix mode), with the Metal HUD logging every frame's interval and GPU time into macron's log. The script waits for the Mac to be thermally nominal before each run (a MacBook Air has no fan), logs the thermal pressure level each second, and summarises frame rate, GPU busy share and interval and GPU time percentiles.

What the sandbox showed of it:

- Both install silently under Macron's Wine and start through DXMT. Both need their own Microsoft shader compiler (`d3dcompiler_47`, or `d3dcompiler_42` and `d3dx11_42`) set to native: Wine's builtin compiler (vkd3d-shader) fails on their shaders (`E5017: Aborting due to not yet implemented feature: Double-to-integer conversion`, `Function "asdouble" is not defined`), after which Superposition stops with `can't load "superposition/system_script.cpp"`. `bench.sh setup` sets the overrides in the benchmark's prefix.
- **M3:** Superposition runs there, with two conditions the sandbox did not show. It stops its own run within a second ("Benchmark stopped", FPS -1, about 120 frames) when its window is not the active app, so the window has to be kept active for the length of the run. And on Thalles's Mac a tiling window manager (AeroSpace) resizes new windows, so "1600x900 windowed" rendered at 960x1172 until the window was made floating; every run's `bench.txt` states the render resolution it really used. One full run with the window active (and tiled, 960x1172): 203 s, 21,218 HUD frames, 59.8 frames a second by the HUD, GPU busy 99%, GPU time a frame median 16.45 ms (p25 15.73, p75 17.48), the benchmark's own count 73.6 fps (min 53.4, max 98.3), thermal pressure reaching level 2 during the run.
- Neither can finish on the sandbox's virtual GPU: Superposition hangs it at frame 9 (`kIOGPUCommandBufferCallbackErrorHang`, then every submission is ignored), Heaven around frame 100 after `Failed to create tessellation raster PSO`. DXMT warns `Experimental non-Apple GPU support` there. Whether they run on the M3 is request 2's first answer.
- The Metal HUD does not work on the sandbox's virtual GPU: with `MTL_HUD_ENABLED=1` DXMT stops after choosing its feature level (the Direct3D 11 probe presents normally without it), and a native Metal program (`tools/perf/gpuload.m`) dies with `Illegal instruction` (x86_64) or is killed (arm64) once the HUD loads. So the HUD's log cannot be tried there. Its format comes from Apple's tech talk and [MetalHUDLogger](https://github.com/InvurseStudio/MetalHUDLogger): `metal-HUD: <frame>,<memory>,<memory>[,<misses>],<interval>,<GPU>,…`.

## Open: what the HUD counts, and a 120-a-second ceiling on DXMT's presents

- **M3:** in the Superposition run the HUD counted 59.8 frames a second while the benchmark counted 73.6. The HUD's frames look like frames shown on the 60 Hz display, not frames rendered: a game drawing faster than the display has its GPU time summed per frame shown (16.45 ms there, about 13.4 ms per rendered frame if the 73.6 is right). So for an uncapped game the HUD's frame rate cannot exceed 60 here and its GPU time a frame is not a rendered frame's. Overwatch's 15.7 ms (57.5 fps by the HUD) was below 60 a second and needs no such correction, as far as that goes.
- **M3:** in the first `pair` pass, `gpuload.exe` through DXMT, presenting with sync interval 0, returned from `Present` exactly 60.0 times a second (its own clock) on all three loads, while the native program ran at 133 to 253. **sandbox:** the same program through DXMT, with the HUD off, ran at 97 (fill) and 210 (draws) frames a second. DXMT's source has no pacing for sync interval 0 (it calls `presentDrawable` straight away and sets `displaySyncEnabled = NO` on its layer), and Wine's Metal view is an ordinary layer-backed subview (`WineMetalView` in `cocoa_window.m`, which in Wine 11.21 has no display link and nothing that paces drawing to the display). The M3 runs had the HUD on, the sandbox runs had it off (the HUD stalls DXMT there). Not established: whether the ceiling is the HUD's, Wine's window path or something of that Mac's. Request 9 measures it.
- **M3, request 9:** the ceiling is not the HUD's. `gpuload.exe --mode draws --sync 0` through DXMT returned from `Present` 117.7 times a second with the HUD off and 120.0 with it on (interval p50 3.8 and 9.8 ms, p95 15.2 and 15.0: bursts, then a wait of most of a refresh); native `gpuload` with the same settings ran at 478 and 482. So something in DXMT's or Wine's window path lets about two presents through per display refresh. Where, is not established; the differences from the native program are DXMT's `framebufferOnly = NO`, its layer being a subview of Wine's view, and DXMT's drawable acquisition on its own thread. It matters for games above 120 frames a second in a window, not for Overwatch's 54 to 75.
- **M3, batch 1 as committed:** the ceiling is at 120, not 60: `gpuload.exe` through DXMT returned from `Present` 120.0 times a second on all three loads (20.0 s, 2,400 frames), whatever the GPU work (0.8 ms for `draws`), while the HUD counted 60.0 presents a second; native Metal with the same layer settings ran at 134 to 248. A 120 ceiling does not hold Overwatch at 60 to 75; it would hold a lighter game at 120 in a window. Request 9 (HUD off and on) is still the test of where it comes from.

## Heat

- **M3, request 12:** five minutes of fixed GPU work through DXMT (`gpuload` `fill`, 12 passes, 1600x900, presented at 60 a second, GPU busy 85%) from a cool start: thermal pressure stayed at level 0 for all 301 seconds, and the GPU time a frame stayed between 13.9 and 14.4 ms from the first half-minute to the last. Superposition, by contrast, reached level 2 within about a minute in nearly every run (batch 1).
- So a GPU-only load at 60 frames a second does not throttle the fanless Air in five minutes, while a whole game does. What the difference is (the game's CPU side under Rosetta, the GPU at 100% instead of 85%, the frame rate uncapped) is not established. If it is the uncapped rate, a frame cap at the display's 60 would keep Overwatch cooler and steadier; that is a test for Thalles's own play (Overwatch's frame limiter), not something measured here.
