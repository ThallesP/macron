# OpenGL call batching (Wine patch 0007)

Each OpenGL call a Windows program makes now waits in a per-thread queue inside `opengl32.dll` until a call that needs an answer comes along, and then the whole queue crosses to Wine's Unix side in one transition. Before, every call crossed on its own, and on these sandboxes a crossing costs about 14 µs (PROGRESS.md, "Gate 1, what the sandbox shows").

Branch `gl-batch`, sandbox `sbx_hzfsgybj` (macOS 26.7.2, "Apple M1 (Virtual)", 3 cores), 2026-11-15. Every number here is from that sandbox.

## What changed

- `runtime/wine/patches/0007-opengl32-Queue-calls-that-return-nothing-and-replay-them-in-one-Unix-call.patch`. It changes Wine 11.21's `dlls/opengl32`:
  - `batch.c` (new, Windows side): `UNIX_CALL` in `thunks.c` and `wgl.c` now goes through `opengl_unix_call()`. That function looks the call up in a table. A call it may queue is copied into the thread's 128 KB queue, with the data it points to. Any other call replays the queue first, then goes through as before.
  - `batch_table.h` (new, generated by `runtime/wine/gl-batch-table.py` from `unixlib.h` and `unix_thunks.h`): one entry per call that may be queued or that changes what may be queued. 1,260 calls take only values; 390 point to data whose size the call itself gives (`glBufferSubData`, `glUniform*v`, `glUniformMatrix*v`, `glLoadMatrix*`, the fixed-size `glVertex3fv`-style vectors); 41 are draws; 29 set vertex array pointers.
  - `unix_wgl.c`: `flush_batch` and `wow64_flush_batch` replay the queue. Each queued call goes through the same entry in `__wine_unix_call_funcs` (64-bit) or `__wine_unix_call_wow64_funcs` (32-bit on WoW64) that it would have reached directly, with the params struct the Windows side built. So nothing is converted twice, and the Unix side needs no code per function.
  - `unixlib.h`, `unix_thunks.c`, `make_opengl`: one new Unix call, `unix_flush_batch`, after `get_pixel_formats`, added in the generator too so a regeneration keeps it.
- `runtime/wine/build-overlay.sh` also builds `opengl32.so` (x86_64) and `opengl32.dll` (i386, x86_64) unpatched and patched. It checks them against Gcenx's: `check-unix-lib.sh` (new) for the Unix library, `check-pe-exports.sh` for the DLLs. Then it packs them into the overlay.
- `internal/wineruntime`: the overlay's `opengl32.so` now also goes into the plain Wine tree. The overlay's Windows modules already go there, and the patched `opengl32.dll` numbers its Unix calls differently from Gcenx's `opengl32.so`, so the two must always travel together.
- Measuring: `glprobe --cost N` (`tools/wow64-gl-probe`), `probe.exe --sprite-size N` (`scenarios/d3d9-fps-probe`) and `tools/gl-batch/measure.sh`.

### What may be queued, and when the queue is replayed

A call is queued only if all of these hold:
- it returns nothing;
- its arguments are values, or point to data whose size is known when it is called (that data is copied);
- the Unix side does not wrap it in a way that touches more than the current context's state.

The queue is replayed before any other call reaches the Unix side. That covers:
- every call that returns something, including `glGetError`, so errors are reported as before;
- every call that reads or writes memory later (`glReadPixels`, maps, `glTexImage2D`);
- `wglMakeCurrent` and `wglDeleteContext`;
- `wglSwapBuffers`, which gdi32's `SwapBuffers` goes through;
- `glFlush` and `glFinish`;
- thread exit (`DLL_THREAD_DETACH` makes a Unix call);
- a full queue.

Queued data larger than 32 KB goes straight through instead.

Draws need two more conditions, because they read vertex arrays that may live in client memory:
- No vertex array in the process was ever given a client pointer. A `gl*Pointer` call made while no `GL_ARRAY_BUFFER` is bound sets a sticky flag, and every draw after that goes straight through.
- Elements draws also need an element array buffer known to be bound, so their `indices` is an offset. The patch tracks that from `glBindBuffer(GL_ELEMENT_ARRAY_BUFFER)` and forgets it on a VAO bind, a buffer or VAO delete, `glPopClientAttrib` and a context change.

While the queue replays, any call that re-enters, such as a debug callback calling GL, goes straight through. `WINE_OPENGL_BATCH=0` turns batching off.

### Why this design

The brief's design is what was built. The alternatives considered:
- **Make each transition cheaper.** Rosetta has no FSGSBASE, so switching `%gs` needs the Mach trap. macOS's own code (errno, `pthread_self`) reads `%gs`, so Wine cannot stay on the TEB's `%gs` while it runs Unix code. Nothing to gain there.
- **Batch inside wined3d.** That would only help Direct3D 8/9 and wined3d's Direct3D 10/11. Doing it in `opengl32` helps every OpenGL program too.
- **Write a replay function per GL function on the Unix side, as command-stream designs usually do.** That would mean thousands of hand-written or generated functions. Here the queue holds the exact params structs the existing thunks already take. The Unix side calls the existing thunks, the WoW64 pointer conversion included. The only per-function knowledge is the generated table: which calls may be queued, and how big their data is.

## Measurements

All runs: `MACRON_OPENGL=apple-software`, `WINEDEBUG=-all` (macron's default), started through `macron launch` (profiles `wow64-gl-probe` and `d3d9-fps-probe`, both on the DXMT tree with Wine's builtin `d3d9` → wined3d → `opengl32`). Runtime macron.5 as `macron runtime install` fetches it. The two builds:
- "stock": Gcenx's `opengl32`, the one macron.5 ships.
- "0007": built on the sandbox by `build-overlay.sh` with patches 0001 to 0007, overlay SHA-256 `473af7c3...`, `opengl32.so` `ec2618d6...`.

Each build was swapped into both runtime trees and both prefixes. `tools/gl-batch/measure.sh 3` ran three rounds and swapped the build order every round. All Wine processes were killed between runs.

### Cost of one OpenGL call

`glprobe32.exe` / `glprobe64.exe --rounds 1 --gets 1 --cost 20000`, a 3.2 core context, drawing into a framebuffer object. Each figure is the time of 20,000 calls, `glFinish` included, divided by 20,000, so queued calls are paid for with their replay. Mean of 3 runs, in ns (each run's figures are in the table below):

| call | 32-bit stock | 32-bit 0007 | 64-bit stock | 64-bit 0007 |
|---|---|---|---|---|
| `glGetIntegerv` (returns a value: never queued) | 15,064 | 15,940 | 15,831 | 15,920 |
| `glUniform1f` | 14,829 | 229 | 15,160 | 162 |
| `glBindBuffer` | 14,651 | 253 | 15,356 | 212 |
| `glBufferSubData`, 64 bytes | 15,308 | 186 | 14,741 | 127 |
| `glUniformMatrix4fv` | 15,477 | 227 | 14,348 | 193 |
| the nine calls of a wined3d draw in Ultimate Custom Night, per call | 15,567 | 273 | 15,472 | 218 |

Queued calls cost 0.13 to 0.27 µs, down from 14 to 15 µs: 55 to 115 times less. A call that returns a value still costs a whole transition, as it must.

### Direct3D 9 with 3,900 one-pixel sprites

`probe32.exe` / `probe64.exe up --sprites 3900 --sprite-size 1 --window 1024x768 --warmup 5 --seconds 10`. Every quad of the scene is 1x1 pixel, so a frame costs its draws and almost nothing in rasterising. The reference is `loadprobe` (`tools/clickteam-games/loadprobe.m`) at `api=gl-sw draws=3900 quad=1x1 uniforms=1`: the same OpenGL work in a native Mac program, without Wine, run once per round.

| | run 1 | run 2 | run 3 | mean | share of loadprobe x86_64 |
|---|---|---|---|---|---|
| probe32, stock | 1.55 | 1.45 | 1.75 | **1.58 fps** | 0.025 |
| probe32, 0007 | 22.16 | 19.31 | 28.13 | **23.2 fps** | 0.37 |
| probe64, stock | 0.55 | 0.57 | 0.57 | **0.56 fps** | 0.009 |
| probe64, 0007 | 0.89 | 1.07 | 0.90 | **0.95 fps** | 0.015 |
| loadprobe, x86_64 (Rosetta) | 50.48 | 58.17 | 80.52 | **63.1 fps** | 1 |
| loadprobe, arm64 | 59.23 | 64.79 | 72.94 | **65.7 fps** | |

The 32-bit program, the path Ultimate Custom Night takes, runs 14.7 times faster: 633 ms a frame becomes 43 ms. It was at 2.5% of the same OpenGL work without Wine and is now at 37%. The sandbox is noisy: loadprobe itself ran anywhere from 50 to 80 fps across the three rounds.

How many calls each draw makes (an `+opengl` trace of 6 seconds, `WINEDEBUG=-all,+opengl` so wined3d's error checks stay off as in the measurement):
- **32-bit**, per draw: `glBindTexture`, `glActiveTexture`, `glBindSampler`, `glBindBuffer`, `glBufferSubData` (0003 turned the buffer map into this), `glDrawArrays`, and 0.4 to 0.8 of each blend, colour-mask and enable call. All of them are queued now. The remaining 43 ms a frame is wined3d's and d3d9's own work on the Windows side, translated by Rosetta, plus replaying the calls on the Unix side.
- **64-bit**, per draw: `glMapBufferRange`, `glFlushMappedBufferRange` and `glUnmapBuffer`, besides the calls the 32-bit trace shows. A map returns a pointer, so it can never be queued, and each one also replays the queue. So the 64-bit probe gains little: about 1 s a frame, 270 µs a draw, is far more than three transitions cost. Apple's software renderer probably synchronises on every map. This is the path patch 0003 already took away from 32-bit programs. Giving 64-bit programs 0003's upload path, on hosts without persistent buffer maps, is the obvious next step. It is not done here; Wine patch 0008 does it (`docs/wd3d-upload64.md`).

Ultimate Custom Night itself was not run: the rules for this work exclude Steam. Its night frame makes about 32,000 calls of the kinds in the table above (PROGRESS.md), so the transitions drop from about 0.45 s a frame to about 9 ms. On the sandbox the frame is then bound by Apple's software rasteriser: loadprobe's night load, 3,900 quads of 1x768 pixels, ran at 2.1 to 2.5 fps.

## Not done, and uncertain

- The patched overlay is not published. `internal/wineruntime/manifest.go` still pins macron.5. Publishing it means a new `RELEASE_TAG` in `release.env`, the Wine build workflow, and a new pin. Not part of this branch.
- With the `d3d` debug channel's ERR on (any `WINEDEBUG` that leaves `err` on, such as `+opengl` alone), wined3d calls `glGetError` after most GL calls on Apple's OpenGL, which has no `ARB_debug_output`. Each of those calls replays the queue, so batching gains less there. macron sets `WINEDEBUG=-all`.
- What the queue may defer was reasoned from the GL specification and Wine's thunks, not proven. These are deferred: GL work that a program on one thread expects another context to see without a flush or a fence (the spec does not promise that either), and synchronous debug-callback messages (they now arrive during the replay). The draw rule is conservative: one client-memory vertex array anywhere in the process turns draw batching off for good.
