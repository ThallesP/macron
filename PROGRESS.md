It is rc4 with an installer that works on a Mac that never had Macron's prerequisites:
- **rc4 could not install on a Mac without Rosetta 2**, which is every new Apple silicon Mac until some Intel program asks for it. ## Gate 1 findings, sandbox, 2026-11-14

- **The 32-bit path cannot be measured on the runner as shipped.** The frame-rate probe (`scenarios/d3d9-fps-probe`, merged from branch `d3d9-fps-probe`) draws 400 alpha-blended sprites per frame through Direct3D 9. On the runner, 32-bit Direct3D 9 runs only through `MACRON_OPENGL=llvmpipe`. That is a Windows OpenGL DLL inside Wine, so it never takes the path that is slow on the M3: Wine's unix-side OpenGL in 32-on-64 mode. wined3d's Vulkan renderer crashes in 32-bit on MoltenVK (`vkCreateBuffer(): Only external memory handle type ..._MTLBUFFER_BIT_EXT and ..._MTLHEAP_BIT_EXT are supported`), and DXVK's d3d9 cannot make a device.
- **Apple's software OpenGL renderer works on the runner** (`Apple Software Renderer`, OpenGL 4.1, from a small native CGL program). Wine could not use it, because winemac's `init_context()` insists on `kCGLPFAAccelerated` even with `AllowSoftwareRendering`. Wine patch 0002 (`runtime/wine/patches`) falls back to the software renderer when that setting is on. With it, the runner runs a 32-bit Direct3D 9 program the way Ultimate Custom Night runs on a Mac: wined3d → Wine's `opengl32` in 32-on-64 mode → Apple's OpenGL.
- **The cause, from Wine 11.21's source.**
  - A 32-bit program cannot use a pointer above 4 GB, and Apple's OpenGL returns mapped buffer memory above it. It has neither `GL_MESA_map_buffer_client_pointer` nor persistent mapping.
  - So for 32-bit programs, `opengl32`'s `wow64_map_buffer` emulates `glMapBufferRange` by copying: into low memory on map, and back on unmap. Without an invalidate flag it also copies the data in first.
  - Without persistent maps, wined3d serves every `NOOVERWRITE` or `DISCARD` buffer map by mapping the whole buffer object, with no invalidate flag. `wined3d_cs_map_upload_bo` cannot use its fast path ("BO is not mapped"), so `buffer_resource_sub_resource_map` maps `resource->size`.
  - So each `DrawPrimitiveUP` copies the whole streaming buffer (at least 512 KB, `SB_MIN_SIZE`) in and out. A 64-bit program uses the driver's pointer directly.
- **Measured on the runner** (sandbox sbx_dcs7vyrm, patch 0002, stock wined3d, the probe in `mix` mode in 32-bit with `WINEDEBUG=+opengl`): **51,844 copies totalling 27,181,187,072 bytes**. Every one was 524,288 bytes, the whole streaming buffer. About 66 frames were drawn in that run (60 warm-up and 3 measured, plus a few), so that is roughly **780 copies and 410 MB copied per frame**. That is consistent with the M3's 5 frames a second at 185% CPU (PROGRESS, "From the MacBook"), but it is the probe's cost: whether Ultimate Custom Night draws the same way is not measured (see "A real Clickteam Fusion game": two other Fusion games' title screens map no buffers at all).
- **How to measure on the runner without fooling yourself.** Three things made the first rounds misleading:
  - Wine processes from killed runs kept running and took the CPU. `pkill -f "probe32\|probe64"` matches nothing, because `\|` is a literal in pkill's pattern syntax.
  - `reg add` followed by `kill -9` loses the value, because wineserver writes the registry only when it exits. Use `MACRON_OPENGL=apple-software`, which waits for the server.
  - Apple's software renderer compiles every new shader with `CVMCompiler`, which takes seconds, so a cold machine's first runs crawl.
  
  The clean method, `/tmp/gltest/iso.sh` on sbx_vfintpyh: a fresh APFS clone of a prepared prefix per run (`STEAM_COMPAT_DATA_PATH`), every Wine process killed by name between runs, three repetitions, a 15 s warm-up, a 10 s measurement, and a 180 s cap.
- **Clean results** (the probe at 960x540, 400 sprites, Apple's software renderer through `MACRON_OPENGL=apple-software`):

  | build | 32-bit `up` | 32-bit `vb` | 32-bit `mix` | 64-bit `mix` |

  | stock wined3d | never finished (3 of 3 hit 180 s) | never finished (3 of 3) | crash, crash, 2.75 fps | 3.30, 3.98, 3.40 fps |
  | patch 0003 | 7.05, 6.76 fps, then one hit 180 s | 7.44, 7.94, 7.47 fps | crash, 6.93 fps, crash | 3.57, 4.09, 2.96 fps |

  Copies traced with `+opengl` (each run has at least 60 warm-up frames):
  - stock 32-bit `up`: 51,588 copies, 27,046,969,344 bytes, about 410 MB per frame;

  With 0003, 32-bit runs faster than 64-bit on the runner's software renderer. Without it, 32-bit mostly never gets through warm-up.

## The 32-bit OpenGL crashes, sandbox, 2026-11-15

Branch `wow64-gl-crash`, one sandbox (sbx_ojvgsegl), runtime macron.3, `MACRON_OPENGL=apple-software`. Every count is starts through `macron launch`, every Wine process killed between starts (`tools/wow64-gl-probe/loop.sh`). Two different crashes turned out to be behind "the 32-bit start-up crash":

- **A winemac bug, fixed by Wine patch 0005 (not in the runtime yet).** When the last reference to an OpenGL context goes away off the main thread, `-[NSOpenGLContext dealloc]` calls Wine's `-clearDrawable`, which retains the dying context in an `OnMainThread` block; the main thread releases it after it is freed and dies in `objc_release` ("c0000005 in system thread"). `tools/wow64-gl-probe` (32-bit, wined3d's context setup without Direct3D) crashed in 23 of 30 starts with the shipped `winemac.so` and 0 of 30 with 0005, starts alternating. The 64-bit build exits 0 but 11 of 20 starts logged the same fault during exit. The Direct3D probe hits it too (its silent exit-5 starts), but rarely. runtime/wine/patches/README.md has the trace.
- **A mode switch between 32-bit and 64-bit code that does not take effect: the probe's main failure, fixed later by Wine patch 0006 ("The mode switch under Rosetta").** In 30 alternating pairs the 32-bit Direct3D probe (`mix --warmup 1 --seconds 1`) failed 14 times with the shipped `winemac.so` (8 of them this crash, 5 exit 1 with no output after `RESULT window: OK`, 1 silent exit 5) and 12 times with 0005 (5 this crash, 3 exit 1, 3 exit 5, 1 stall). In 12 more starts with 0005 and `+seh`, all 4 failures were this crash, 2 in each direction; the silent exit-5 ones are the 64-to-32 direction, where Wine cannot dispatch the exception ("Exception frame is not in stack limits"). The exit-1 starts were not classified. The faulting instruction says which way the switch failed:
  - Direct3D probe: `Unhandled page fault on read access to 00002DC1 at address 7BF41239`, every time. `wow64cpu.dll` was loaded at `7BF40000`; `+0x1239` is `movl cs32_sel(%rip),%edx` in `unix_call_32to64`, 64-bit code. Read as 32-bit code, `8b 15 c1 2d 00 00` is a load from the absolute address `0x2dc1`: the thread came through the 32-to-64 far jump of Wine's Unix-call thunk still in 32-bit mode.
  - The crash in patch 0004's notes (`addr=7A77ADEF` in 32-bit `opengl32.dll` at `7A6D0000`, reading `0BEC988B0014A018`, seen again here with `cs=002b`, the 64-bit selector) is the other way. `+0xAADEF` is `mov %fs:0x18,%eax` (`64 a1 18 00 00 00`) at the start of `set_context_attribute()`, which every generated GL thunk calls right after its `UNIX_CALL`. Decoded as 64-bit code, `64 a1` takes an 8-byte address, `0x0bec988b00000018` (the next instruction's bytes), plus the fs base `0x14a000`: exactly the reported address. So the thunk came back from `unix_call_32to64` still in 64-bit mode. `rip=7a83c7307a83c670` (with the command stream thread) is the same: a 64-bit `ret` popping two 32-bit values.
  - Not Wine's selector, for the 32-to-64 direction: that jump goes through a read-only thunk whose target and selector are set once at start-up (`BTCpuProcessInit`) and work for every other call. For the 64-to-32 direction the selector comes from the saved 32-bit context; a `wow64cpu.dll` that traps when it is not `cs32_sel` never trapped, but it only ran against the small program (15 starts), which never showed this crash, so that direction is not ruled out.
  - Not every transition. 20 starts of 200,000 system calls each (`--syscalls`, the same far jumps through the syscall thunk) never crashed, without OpenGL or after one OpenGL round; nor did 15 starts with a thread making system calls next to a thread doing OpenGL (`--syscall-thread`; its 6 crashes were all the winemac bug). 20 starts that compile and draw 200 new shader programs each (`--shaders 20`, with 0005) never crashed, so Apple's shader compiler generating x86 code is not enough to trigger it either.
  - So under Rosetta a far jump between Wine's 32-bit and 64-bit code segments sometimes does not switch modes, in a way that wined3d's device creation triggers and nothing smaller tried here did. That points at Rosetta, not Wine, but what triggers it is not established, and whether a Mac with a real GPU (hardware OpenGL, no software shader compiler) sees it is unknown.
- **Wrong leads, for the record.** The `iretq` variant was measured only against the small program (16 of 30 crashed), whose crashes all turned out to be the winemac bug, so it says nothing about the mode switch. The first fix tried for the winemac crash (reading the view on the main thread in `-setView:` and `-clearDrawable`) was dropped: the zombie output named the context, not the view.
- **What Macron can do now.** `MACRON_OPENGL=llvmpipe` avoids both crashes (Mesa inside the 32-bit process never calls Wine's 64-bit OpenGL); the frame-rate check keeps `startAttempts: 3`. 0005 was released as [runtime-wine-11.21-macron.4](https://github.com/ThallesP/macron/releases/tag/runtime-wine-11.21-macron.4) and is pinned. `runtime/wine/build-overlay.sh` with 0001 to 0005 passed every check on the sandbox (the patched `winemac.so` is a drop-in for Gcenx's; `wined3d.dll` exports the same 377 symbols).

## The mode switch under Rosetta, sandbox, 2026-11-15

Branch `rosetta-mode-switch`, one sandbox (sbx_uqstb45i), runtime macron.4, `MACRON_OPENGL=apple-software`. Every start went through `macron launch` with every Wine process killed and the prefix replaced by a fresh copy first; the `wow64cpu.dll` under test was copied into both runtime trees and the prefix; builds alternated start by start, the first one rotating each round. The candidates were built on the sandbox with the overlay's toolchain (llvm-mingw 20261020, the overlay's configure flags).

- **How Wine 11.21 switches modes (`dlls/wow64cpu/cpu.c`).** Every system call and Unix call from 32-bit code enters 64-bit code through a 12-byte thunk built in `BTCpuProcessInit`, `ljmp *addr` (`ff 2d`, a far pointer to `syscall_32to64` or `unix_call_32to64` and the 64-bit selector `0x2b`). Both come back with `ljmp *(%r14)` (`41 ff 2e`) to the saved 32-bit `eip`/`cs`; only the path after a context change (`WOW64_CPURESERVED_FLAG_RESET_STATE`) and a thread's first entry (`BTCpuSimulate`) use `iretq`. On macOS the 32-bit selector is an LDT entry Wine allocates (`ldt_alloc_entry(ldt_make_cs32_entry())` in `signal_x86_64.c`), and every 32-bit thread gets an LDT entry of its own for `%fs`. Both crash sites are the far jumps: the fault at `wow64cpu.dll+0x1239` is the thunk's `ljmp` in, the fault in `set_context_attribute()` the `ljmp *(%r14)` back.
- **Iret both ways removes the crash.** `probe32.exe mix --warmup 1 --seconds 1`, 40 rounds:

  | `wow64cpu.dll` | failed starts |
  |---|---|
  | macron.4's (Gcenx's), `ljmp` both ways | 25 of 40 (10 crash, 6 exit 1, 6 exit 5, 3 stall) |
  | A: `iretq` out, `ljmp` in | 14 of 40 (7 crash, 7 exit 1) |
  | B: `iretl` in (`pushfl; pushl $cs; pushl $target; iretl`), `iretq` out | 0 of 40 |
  | C: `lret` in, `iretq` out | 0 of 40 |

  With `WINEDEBUG=+seh`, 12 more rounds: macron.4's 3 of 12 failed, A 3 of 12, all six the page fault at `unix_call_32to64`'s `movl cs32_sel(%rip)` (the way in); B and C 0 of 12. So the far jump in fails more often than the one back, changing only the way back removes the exit-5 starts but not the crash, and both forms that avoid the far jump in work. B became Wine patch 0006 (one form both ways); `runtime/wine/patches/README.md` has the details. `build-overlay.sh` with 0001 to 0006 passed every check on the sandbox (`wow64cpu.dll` exports the same 9 symbols as Gcenx's), and the `wow64cpu.dll` in that overlay failed 0 of 15 starts against 10 of 15 for macron.4's in one more alternating batch. B, C and the overlay's build together: 119 starts, no failure; macron.4's in the same batches: 38 of 67 failed.
- **No regression.** 32-bit probe, 10 s measured: B 8.97 fps on average (6 of 6 starts, 8.57 to 9.11), C 9.07 (6 of 6), macron.4's 8.93 (4 of 6; the other 2 failed). 64-bit probe: 20 of 20 starts with B and 20 of 20 with macron.4's, 4.49 fps each (a 64-bit process does not load `wow64cpu.dll`).
- **Not the trigger: LDT changes.** Because the 32-bit selector and every thread's `%fs` live in an LDT that Rosetta emulates, `tools/wow64-gl-probe` got `--churn` (a thread starting and joining empty threads, each one an `i386_set_ldt`, while the other thread makes system calls). 10 starts with macron.4's `wow64cpu.dll`, about 4,100 threads and 300,000 system calls each, never failed. Why Rosetta misses the mode change on a far jump during wined3d's device creation is still unknown; the fix does not depend on it.
- **Not done.** The overlay with 0006 is not published and the runtime pin is unchanged (`release.env` says macron.5). `runtime/wine/build-overlay.sh` now builds `wow64cpu.dll` and checks its exports; the runtime copies it into both trees like `wined3d.dll`. A Mac with a real GPU (hardware OpenGL) is unchecked, as is whether `startAttempts: 3` in the frame-rate check can go back to 1 once 0006 is pinned.

## SuperTuxKart's broken frames, sandbox, 2026-11-14

The SuperTuxKart scenario failed now and then in CI (runs on f4f6132 and fb001cf, 2 of 19 runs): the captured menu was STK's clear colour (100,101,140) with the menu missing or squashed into long slivers, SSIM about 0.09.

- **The broken frames come in bursts.** The check takes one picture; a harness on two sandboxes instead captured the menu's window every 70 to 150 ms for 30 to 60 s after the layout line and compared each picture with the Windows reference. Without a fix, every launch has a burst of about one second of broken frames every 8 to 12 s, and fine frames in between: 110 of 885 pictures broken (12%) over 4 launches, 2 to 3 bursts each. One picture taken at a random moment fails about one time in ten, as in CI. 10 full `macron-check` runs on the sandboxes gave 1 failure (SSIM 0.097), and screenshots of the desktop a few seconds later show the right menu.
- **The cause is MoltenVK's Metal heaps.** With `MVK_CONFIG_USE_MTLHEAP=0`, MoltenVK does not place buffers in Metal heaps, and no picture was broken: 0 of 2,484 over 7 launches (about 330 s of menu), and 0 of 936 over 2 launches with the profile that sets it, whose 4 full `macron-check` runs from a fresh prefix all passed (SSIM 0.971). Ruled out, each with 2 to 4 launches that still had bursts: wined3d's command stream thread (`csmt=0x0`, 4 launches), Metal argument buffers (`MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS=0`, 89 of 721 broken), synchronous queue submits (`MVK_CONFIG_SYNCHRONOUS_QUEUE_SUBMITS=1`, 50 of 410; it is MoltenVK 1.4's default on macOS already). The `VkDescriptorPool exhausted ... Allocating descriptor dynamically` warnings are in passing and failing runs alike.
- **What exactly races under heaps is not known.** With heaps, MoltenVK gives every `VkBuffer` its own Metal buffer placed in the memory's heap (hazard tracking on); without them, every buffer in a `VkDeviceMemory` is a range of one Metal buffer. The broken frames look like wrong vertex transforms (the GUI's quads stretched towards infinity, as with a near-zero `w`), so the fixed-function constants or the streamed vertices are probably read before they are written, or from the wrong place, but that was not traced.
- **Specific to SuperTuxKart so far.** The 64-bit Direct3D 9 probe through the same renderer with heaps on (`vb`, `mix` and `up`, 5 launches, about 1,100 pictures) never broke. So the switch is in SuperTuxKart's profile, not in Macron's defaults for wined3d's Vulkan renderer. A real Mac's GPU (not the runner's paravirtual one) is unchecked.

## The Steam Play switch, sandbox, 2026-11-15

Sandbox sbx_qsjpicyv (macOS 26.7.2, Steam build 1794536281 from Valve's DMG in /Applications, the `macos-signed-2` variant), signed in to the test account. `steamplay/README.md` describes the result; this is how it was found and what was measured.

- **Where Steam Play is switched off.** `steamclient.dylib` (arm64 half, `LC_UUID` 221faa3a-6a2c-36c9-9130-b0a45028af1b) names its compat functions in profiling strings, so `CCompatManager::BIsCompatibilityToolEnabled` is found by its own name. It first reads a byte at offset `0x810` of the manager. That byte has 13 readers (`OnAppConfigInitialized`, `OnLicensesUpdated`, `OnPostLogonState`, `FindToolForTargetApp`, ...) and one writer besides the "Disabling compatibility layer." path: the constructor, which stores `V_strnicmp(<this platform's oslist>, "linux") == 0`. So the whole system is gated on the platform being Linux, decided once. No setting feeds it except the platform name itself.
- **One instruction is enough for Install and Play.** Changing that `cset w8, eq` (at `0x6bab8c`) to `mov w8, #1` when `steamclient.dylib` is loaded brought the machinery up: `compat_log.txt` shows `CCacheOffSteamPlayStateJob` processing Valve's tool lists and ignoring every Proton and Steam Linux Runtime "as it's for a different target platform linux". No function is hooked. NotProton hooks eight functions; Macron needs none of them because its tool is a local `compatibilitytools.d` tool with `to_oslist` `macos` and an AppID 0 mapping, which is the case Steam's own code handles.
- **Steam did not scan Macron's tool folder.** The Mac client scans `/usr/share/steam/compatibilitytools.d`, `/usr/local/share/steam/compatibilitytools.d`, `STEAM_EXTRA_COMPAT_TOOLS_PATHS` and `compatibilitytools.d` under its program folder, and logs nothing when it finds no tool. With `STEAM_EXTRA_COMPAT_TOOLS_PATHS` set to `~/Library/Application Support/Steam/compatibilitytools.d`: `Processing local tool list at .../macron/compatibilitytool.vdf`, `Registering tool macron, AppID 0`, `Command prefix for tool 0 "Macron" set to: "'.../compatibilitytools.d/macron/.'/macron run "`. Phase 1's "Steam reads the mapping" was the mapping only; the tool itself had never registered.
- **Then the buttons worked at once.** Ultimate Custom Night's page went from a greyed INSTALL with "AVAILABLE FOR Windows" to a blue INSTALL with "SPACE REQUIRED 262.02 MB"; Steam's dialog installed it to `steamapps/common/Ultimate Custom Night` in 24 s; PLAY started `macron waitforexitandrun .../Ultimate Custom Night.exe` with `STEAM_COMPAT_DATA_PATH` set, so the prefix is `steamapps/compatdata/871720/pfx`; the title screen and the character-select menu drew; Steam showed "Running" and STOP.
- **Steam's Stop button needed the second instruction.** Stop left the game running and the page on "Stopping". Steam's terminator is a ladder: `-[NSRunningApplication terminate]` on the process it started, then SIGINT after 2 s, SIGTERM after 1 s, a kill after 1 s. Its start function returns failure when the first step does (`bl <terminate helper>; tbnz w0, #0, <carry on>` at `0x119c84c`), and `macron` is not an application, so nothing else happened. Asking macOS to quit the game's own `wine` process did close it, so the path is sound for Mac applications. With the `tbnz` made an unconditional branch, Steam carries on to SIGINT. `macron` then had to tell the Wine server to end the prefix's programs before waiting for its child: the game is not the process `macron` started (Wine's `start.exe` is), and it holds macron's output pipe open, so macron sat until Steam's kill (5 s). With that fixed the game is gone 4 s after Confirm, macron exits 130, and Steam logs `Remove 871720 from running list`. Only the game's own processes end (a process list before and after).
- **Loading the library.**
  - Valve signs `/Applications/Steam.app/Contents/MacOS/steam_osx` (the bootstrapper) with the hardened runtime and without the entitlement that allows `DYLD_INSERT_LIBRARIES`. The client it starts (`~/Library/Application Support/Steam/Steam.AppBundle/Steam/Contents/MacOS/steam_osx`) is signed by Valve with no hardened runtime (`flags=0x0`).
  - The bootstrapper replaces itself with the client (same pid), and the client replaces itself once more before it loads `steamclient.dylib`: a test library logged the same pid three times.
  - **The sandbox has SIP off and is lenient**: there Valve's untouched, hardened Steam.app loaded the test library from `DYLD_INSERT_LIBRARIES`. On a Mac with SIP on it would not, so the design follows Apple's rule and NotProton's practice (sign ad hoc), and the sandbox cannot confirm either the need or the sufficiency.
  - With SIP off, macOS's own programs also honour the variable and abort on a library without an arm64e half (`launchctl`, `nohup`): Steam's children died that way and Steam showed "Unexpected Transport Error" until the library started taking itself out of the environment.
  - After `macron steam enable` (three of Valve's files changed, one file added, `codesign`: `Signature=adhoc`), Steam started from LaunchServices stays signed in, keeps the `macos-signed-2` package, and logs `Steam Play is on`.
  - After `macron steam disable`: every file of Steam.app has its SHA-256 from before, `codesign --verify --strict --deep` passes, `spctl -a -vv`: `accepted, source=Notarized Developer ID`. `config.vdf` differs from its backup only in Steam's own server list.
- **Tooling.** `ci/steam-play/drive.swift` posts clicks and keys, captures a window with rectangles blacked out, and finds text in a window with macOS's Vision framework, so `ci/steam-play/steam.sh` presses "INSTALL", "Install", "PLAY", "STOP" and "Confirm" by what the window says. Traps that cost time: macOS's "find devices on local networks" dialogs sat on top of Steam's login window and took the clicks; a click on the page's activity box focuses a text field (nothing was typed there); a key press with Command leaves the modifier set for later synthetic clicks unless they clear it; and a first version of the "back to PLAY" check matched the "PLAY TIME" caption while the button still said STOP, so it now reads the button itself.
- **The game on the sandbox.** Ultimate Custom Night drew its title screen and menu on the runner without `MACRON_OPENGL` set. Which renderer that was, and its frame rate, are gate 1's next step.

What it lacks is an OpenGL that uses it: Apple's OpenGL on the sandbox rasterises on the CPU, and that alone holds a night to about 2 fps with no Wine involved. - **What Macron's side costs, with no GPU involved** (`tools/wow64-cost`, sbx_dljon6jn, three alternating rounds each). Every Windows system call costs about 20 to 25 µs: `VirtualQuery` 24.5 to 27.8 µs, `SwitchToThread` 18.8 to 20.6 µs, a wait on a signalled event (a wineserver round trip; this Wine has no esync or msync) 82 to 95 µs. Timed piece by piece in a native x86_64 Mac program (`native.c`, under Rosetta, on the same machine):
  - a plain macOS system call: 5.6 to 5.9 µs under Rosetta, 0.14 µs in arm64;
  - the `thread_set_tsd_base` Mach trap (`0x3000003`) that Wine's dispatchers make **twice** per transition to switch `%gs` between the TEB and macOS's thread data: 5.7 to 6.1 µs;
  - `fxsave64`+`fxrstor64` 1.3 µs (Rosetta reports no XSAVE, so Wine uses these); `stmxcsr`+`ldmxcsr` 1.4 µs; `pushfq`+`popfq` 9 ns.
  
  Rosetta has no FSGSBASE (CPUID leaf 7, and `rdgsbase`/`wrgsbase` fault), so the trap is the only way to switch `%gs`. Wine's system call dispatcher (`ntdll.so` at `0x2cfxx`) does two traps, an `fxsave`/`fxrstor` and three `ldmxcsr`: about 20 µs before the call does anything, which accounts for what was measured. Its Unix call dispatcher (`0x2d390`), which every OpenGL call from a Windows program goes through, does two traps, one `stmxcsr` and two `ldmxcsr`: about 14 µs. **At about 32,000 OpenGL calls a night frame that is about 0.45 s a frame, whatever the GPU.** It matches the game's profile: 57% rasterising and most of the rest in Rosetta's runtime.
- **What this does not show.** These sandboxes are virtual machines, and GitHub's macOS runners are too. Whether Rosetta's system calls cost 5.8 µs on a Mac that is not a virtual machine is not measured; if they cost a tenth of that, the night is a few dozen milliseconds of transitions and the GPU path decides. Thalles's MacBook is off limits, so `native.c` (built for x86_64, about ten seconds) is the measurement to take there, and the frame counter (`show-fps`) gives the game's own number.
- **Started with Steam's Play button** (sbx_dljon6jn, `tools/clickteam-games/ucn-play.sh`: `steam.sh play`, macron's `show-fps` on, title, menu and night measured from macron's launch log, Steam's STOP at the end; the game went through the Steam bridge's `steam.exe`):
  - On the path Macron picks on a sandbox (no hardware OpenGL, so no wined3d adapter) the game draws with Clickteam's own software display: Play, the title, Enter, the menu, GO! and a night all worked, but `show-fps` logs nothing, because it counts wined3d's frames and wined3d draws none there.
  - With the prefix allowed Apple's software OpenGL (one start with `MACRON_OPENGL=apple-software` writes `AllowSoftwareRendering` into it, as on qsjpicyv), Play gives wined3d's counter: menu 1.11 to 1.50 fps, night 0.79 to 0.85 fps in two starts, the same as started outside Steam on qsjpicyv (1.1 to 1.4, 0.6 to 0.8). The warning screen moved on to the menu during the 15 s settle, so the "title" window of those runs is mostly the menu (1.39 and 1.50 fps).
  - Two traps on the way, both in the test tools: `steam.sh play` leaves Steam in front, and keys went to Steam; and with the bridge there are two applications named `wine` (the game and `steam.exe`), and `drive activate wine` brought the windowless one forward, which macOS ignores anyway while Steam is the active app. `drive activate` now prefers the process that owns a window and falls back to System Events (`set frontmost ... whose unix id is ...`).
- **The fix: Wine patch 0007, OpenGL call batching** (an Opus 5.5 subagent, branch `gl-batch`, sbx_hzfsgybj; `docs/gl-batch.md`). opengl32's Windows side queues calls that return nothing and whose arguments are values or sized data (copied), and replays the queue in one Unix call before anything that answers, reads memory later, changes context or swaps; draws are queued only while no vertex array uses client memory. `WINE_OPENGL_BATCH=0` turns it off. Measured (3 alternating rounds, `MACRON_OPENGL=apple-software`):
  - cost per GL call, 32-bit: `glUniform1f` 14.8 to 0.23 µs, `glBindBuffer` 14.7 to 0.25, `glBufferSubData` 15.3 to 0.19, the 9 calls of one Ultimate Custom Night draw 15.6 to 0.27 µs per call; `glGetIntegerv` (never queued) 15.1 to 15.9. 64-bit alike.
  - the Direct3D 9 probe with 3,900 one-pixel sprites (no rasterising cost): 32-bit 1.58 to 23.2 fps, against 63.1 fps for `loadprobe` x86_64 doing the same GL work with no Wine (0.025 to 0.37 of it). 64-bit only 0.56 to 0.95: its draws map buffers, which return a pointer and cannot be queued (the 64-bit counterpart of 0003 is the next step there).
  - `d3d9-fps-probe` (SSIM 0.995, every control rejected), `d3d11-probe` and `openttd` pass with it; no check changed.
  - Merged to main (7ba00f0), built and published as [runtime-wine-11.21-macron.6](https://github.com/ThallesP/macron/releases/tag/runtime-wine-11.21-macron.6) by the Wine build workflow ([run 43774736211](https://github.com/ThallesP/macron/actions/runs/43774736211)), pinned (964a7f9); [Scenarios run 43776483837](https://github.com/ThallesP/macron/actions/runs/43776483837) is green on it. It is not in v0.3.0.
- **Ultimate Custom Night with 0007** (sbx_v276s2af, fresh, Steam from Valve's DMG, signed in, v0.3.0 installed from the release, then macron from main with the macron.6 runtime; `MACRON_OPENGL=apple-software`; batching off (`WINE_OPENGL_BATCH=0`) and on, alternating, 3 starts each; `docs/proof/gate1-batching-sbx_v276s2af/`).   | batching on | 2.02, 1.70, 1.58 | 1.23, 1.31, 1.08 |

  The third pair ran while Spotlight indexed the new disk (`mds` at 50 to 80% of a core). The night's frame time goes from about 1.2 s to about 0.8 s: the 0.4 s saved is 32,000 calls at 14 µs, as predicted. **Where the rest goes** (`sample`, batched, `tools/clickteam-games/sample-paths.py`): the game's thread spends 87% (menu) and 89% (night) inside Apple's software rasteriser (`GLRendererFloat`), against 57 to 61% before; Wine, Rosetta outside OpenGL and the Wine server together are about a tenth.
- **What the sandbox can and cannot show, plainly.** The sandbox's GPU is not what limits the game: a native Metal program draws a night's load on it at 165 fps (`loadprobe`). What the sandbox lacks is an OpenGL that uses that GPU: Apple's OpenGL there rasterises on the CPU, and every Direct3D 9 path Macron has (wined3d on OpenGL) goes through it. After 0007, 88% of the game's thread is that CPU rasteriser, so on a sandbox Ultimate Custom Night cannot reach 60 fps on Macron's default path, and the remaining cost is not Macron's side. On a real Mac, OpenGL runs on the GPU and the transition cost may differ; both are what `macron diagnose` and the frame counter measure on Thalles's Mac. 64-bit Direct3D 9 games gained less from 0007 (their buffer maps could not be queued).
- **Wine patch 0008, 64-bit buffer uploads** (an Opus 5.5 subagent, branch `wd3d-upload64`, sbx_y2bxfj2u; `docs/wd3d-upload64.md`). Without persistent maps (Apple's OpenGL has none), 64-bit wined3d handed every `DrawPrimitiveUP` map to its command stream thread and waited twice a draw (about 150 µs), and the map's own OpenGL calls cost about 80 µs more. 0008 gives 64-bit the heap-memory upload path 0003 gave 32-bit, so the upload becomes a `glBufferSubData` that 0007 queues. Probe at 3,900 one-pixel sprites: 64-bit 1.06 to 34.2 fps, 32-bit unchanged (28.9, 29.8); `loadprobe` x86_64 70.4. `d3d9-fps-probe`, `d3d11-probe`, `openttd` pass; no check changed. Two things to know: the frame-rate check's ratio (32-bit over 64-bit, at least 0.8) is now about 1.0 instead of about 2.5, close to Windows' 0.885, so it has less margin on CI; and a program that maps a range with no-overwrite and writes only part of it would upload undefined bytes for the rest, as 32-bit programs have since 0003. Merged (f7fc8a3); published as [runtime-wine-11.21-macron.7](https://github.com/ThallesP/macron/releases/tag/runtime-wine-11.21-macron.7) ([Wine build run 43790298532](https://github.com/ThallesP/macron/actions/runs/43790298532)) and pinned; [Scenarios run 43791641486](https://github.com/ThallesP/macron/actions/runs/43791641486) is green on it (all six, the frame-rate check included). ## How a sandbox logs in to the test account

Every sandbox is a new device. Since 2026-11-15 Steam Guard is off on the test account, and the login needs only its name and password; no code and no CAPTCHA were asked for on sbx_qsjpicyv. If either ever appears, stop that login and leave it for Thalles: never guess a code or retry in a loop.

- **Credentials:** `~/.config/macron/steam-test-account` (mode 600) on the dev machine; copied with `sbx scp` to a mode-600 file on the sandbox; GitHub secrets `STEAM_TEST_USER`, `STEAM_TEST_PASSWORD`, `STEAM_TEST_EMAIL` for the `Steam Play` workflow (daily on main, and manual runs). They never appear on a command line, in a log or in an artifact.
- **Logging in:** `ci/steam-play/steam.sh login` dismisses macOS's local-network dialogs, types the two fields from the file (`drive type-value`), and waits for a new `[Logged On]` in `logs/connection_log.txt`.
- **The account's name on screen:** Steam's top bar, the friends list and the activity feed of a game page show the profile name. Screenshots are taken per window with those areas blacked out, and the workflow reads every screenshot back and drops any that still shows the name.
- **One machine at a time.** While a game of the account runs on one machine, Steam on every other machine signed in to it shows the game as "Running" with a CONNECT button (Remote Play) where Install or Play would be. A gate 3 run on a fresh sandbox failed its stock-Steam check that way while the `Steam Play` workflow was playing the game. So that workflow runs every morning and by hand, not on every push, and hand runs on sandboxes wait for it.
- **The account owns:** Ultimate Custom Night (871720) and Endless Sky (404410, free, Mac-native, the regression game; OpenTTD is no longer free on Steam). Both added with the store page's "Add to Library".
